## 宿題

- 取り組んだレベル：基礎
- やったこと：
  `app/tools.py` の `search_glossary` の docstring を、1か所だけ変えた。「query には調べたい用語を**1つだけ**入れる」→「**まとめて**入れる」（36行目。ほかの行や INSTRUCTIONS は変えていない）。
  同じ質問「LoRAとQLoRAとPEFTの違いは？」を `--trace` 付きで、変更前に2回、変更後に1回実行して比べた（モデルは `gemini-3.5-flash-lite`）。
  結果を見る前に予想を書いた：`search_glossary` は1回、引数は質問文そのまま、`requests=2`、回答は揃う。
  最初に、docstring ではなく40行目の返り値（エラー文）の「1つ」を書き換えてしまったが、実行の前に `git diff` で気づき、元に戻した。
  変更後の効果を理解するため、ツールの返り値を API を使わずに直接実行して確かめた（`search_glossary('LoRA QLoRA PEFT')` と、4用語の場合）。
- 結果：
  変更前（2回とも同じ）：`search_glossary` を `'LoRA'`、`'QLoRA'`、`'PEFT'` の3回。`tool_calls=3`、`requests=2`、入力トークン 1581。回答は3用語を説明した（文面と末尾の表記は、2回で少し違った）。
  変更後（1回）：`search_glossary({'query': 'LoRA QLoRA PEFT'})` の1回。`tool_calls=1`、`requests=2`、入力トークン 1127（約29%減）。回答は3用語を説明した。
  予想との比較：回数、`requests`、回答の質は当たった。引数は外れた（質問文そのままではなく、モデルが用語だけを取り出して、スペースでつないだ）。
  ツールを直接実行：`search_glossary('LoRA QLoRA PEFT')` は、PEFT・LoRA・QLoRA の3件を1回で返した。4用語（`'LoRA QLoRA PEFT RAG'`）では、4件の予想に対し、返ったのは**3件**（RAG が落ちた）。
  変更後の実行で 503 が出た（10:23、10:28 に失敗、10:30 に成功）。
- 気づき・疑問：
  docstring を1語変えただけで、ツールの呼ばれ方が「3回」から「1回」に変わった。`requests` は2のまま変わらず、減ったのは `tool_calls` と入力トークンだった（トークンが減ったのは、呼び出しと結果の分が減ったためと推測したが、確かめていない）。
  3用語が1回で揃ったのは、docstring を変えたからではなく、ツールの実装が、まとめた入力でも当たる作りだったから。`_normalize` が空白を消し、`partial` の条件 `n in q` が「用語名がクエリの中にあるか」を調べるため、`'LoRA QLoRA PEFT'` で3件が当たる。最初は `_normalize` をトークンの処理だと考えていたが、LLM とは関係のない、ツール内部の文字列の処理だった。
  4用語では、`MAX_RESULTS = 3` により、当たった用語が4件でも先頭の3件で切れた。エラーも「見つかりません」も出ず、黙って1件が落ちる。docstring が「まとめて入れてよい」と書いても、ツールの実装には件数の上限があるため、両者が噛み合わない場合があった。
  疑問：1回ずつの実行で、再現するかは確かめていない。4用語のとき、モデルが「3件しか返らなかった」ことに気づいて、再検索するかも確かめていない（API を使う `--trace` で試す必要がある）。
  第1回の疑問「生成AIに許可しますか、と聞かれたとき、何をもって判断するか」との関係：文章を1語変えるだけで、モデルの行動が変わり、予想とも違った。承認を挟む仕組み（human-in-the-loop）や、モデルやエージェントの実行結果を検証する必要性の根拠に、つながると感じた。今後の講義・演習で、この判断の材料を確かめたい。
